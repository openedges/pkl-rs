# Stage137 module diagnostics and authored semver

This local checkpoint records module diagnostics and authored semver validation. The earlier Stage136 full-ready replay remains historical evidence for its own source and is not a replay of this changed engine.

The shared runtime now distinguishes the standard file, HTTP and generic URL key profiles. File-key selection validates the decoded scheme-specific part; generic URL rejection occurs at resolution, while HTTP request construction remains explicitly unsupported. URL glob imports receive their nonglobbable diagnostic before URL I/O. Missing-module diagnostics use the selected key's once-decoded path for the backslash hint and preserve the original declaration frames. The native development Host opts into these shared operations; custom opaque Host handles retain their ownership.

`pkl:semver` compiles the exact pinned upstream Pkl source through the authored-module path, preserving distinct class/property and method namespaces, singleton identity and source locations. The same path now carries the evaluator's power-assertion setting into authored standard-library compilation. The checkpoint adds no native semver algorithm and no Java production fallback. The separate opt-in internal-error catch implementation is not included.

The public `ModuleKeyKind` enum gains three variants. Downstream exhaustive matches require changes; this is not an API-neutral change. Rust probe encoding/decoding and both shared JavaScript transport validators recognize the new kinds. The JavaScript checks preserve opaque handles, including unpaired UTF-16 units, and reject malformed descriptors before consuming completion tokens.

## Scope and remaining gaps

Standard file glob traversal and HTTP/generic URL source I/O remain unsupported by the bounded development Host. HTTP/generic hierarchical metadata, non-default filesystem providers, authority/query/fragment and opaque file conversion cases are not established by these controls. Existing file existence and canonical-resolution paths do not implement all Java policy callbacks; this checkpoint does not establish custom security-policy or root-directory confinement compatibility. File factory case matching and default policy matching deliberately differ, as they do upstream.

The planning-time source manifest records 13 original implementation/test destinations, two differential harnesses, three JavaScript files and `PLAN.md`: 19 nonfixture files, plus 530 captured fixtures. The power-assertion correction shares `src/vm/stdlib_modules.rs`; it is not an additional destination. Its `PLAN.md` hash predates the final documentation, and it does not include the refreshed `compatibility/m2-language.json`. The final `source-files.json` separately pins the current implementation, fixtures, documentation and language manifest; `publication.json` pins the published archive and receipts.

Stage136 remains historical full-ready evidence: 4,483 acquired cases, 4,395 passes, 12 mismatches, 74 candidate-unsupported and 2 oracle errors; integrity exit 0, strict full gate exit 1 and 1,743 unmet conditions. Its manifest records 475 requirements (15 implemented, 42 partial, 418 unimplemented) and 4,586 contracts (4,483 ready, 71 unimplemented, 32 unmapped), with 814 cases lacking requirement links. This bounded checkpoint does not recompute that gate or establish full M2/API, release-platform or performance completion. Local evidence is not hosted CI evidence; archive integrity and byte pins do not establish complete compiler/runtime dependency closure.
