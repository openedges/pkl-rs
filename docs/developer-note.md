# pkl-rs 개발자 노트 — 첫 구현에서 재작성까지

기준일: 2026-11-23

## 요약

Apple Pkl을 Rust로 다시 구현하는 일을 코딩 에이전트로 두 번 시도했고, 두 번째에 완성했다. 결과물은 CLI, Rust API, Node.js N-API 애드온, WebAssembly 패키지다.

- **첫 구현** (`gitlab.chipsketch.com/research-team/pkl-rs-0.31.0`)은 12일 만에 호환성 테스트를 통과했지만, 9개월 반이 지나도록 성능과 안정화를 끝내지 못했다.
- **재작성판** (`gitlab.chipsketch.com/research-team/pkl-rs`)은 빈 저장소에서 다시 시작해 5주 만에 전 제품을 만들었다. Apple의 native-image보다 빠르고 메모리를 덜 쓴다.

| 날짜 | 구현 | 전환점 |
| --- | --- | --- |
| 2026-02-04 | 첫 구현 | 시작 |
| 2026-02-16 | 첫 구현 | 호환성 테스트 666/666 통과 |
| 2026-06-16 | 첫 구현 | bytecode VM을 기본 엔진으로 전환 |
| 2026-08-15 | 첫 구현 | 전수 실측, 실패 193건 확인 |
| 2026-10-06 | 첫 구현 | 성능 최적화 중단 |
| 2026-10-20 | 재작성판 | 시작 |
| 2026-11-23 | 재작성판 | 성능 목표 15/15 달성 |
| 2026-11-23 | 첫 구현 | 마지막 커밋. 시작한 지 9개월 반 |

두 시도를 가른 것은 에이전트의 능력이 아니라 오라클, 곧 정답과 대조하는 테스트였다. 첫 구현은 Pkl이 제공하는 기본 테스트만 가지고 시작해 오라클이 얇았고, 검증하면서 하나씩 쌓아야 했다. 재작성판은 그렇게 쌓인 오라클과 실패 기록 위에서, 판정 규칙부터 세우고 시작했다.

## 프로젝트

pkl-rs는 Java로 구현된 설정 언어 Apple Pkl을 JVM 없이 쓸 수 있도록 Rust로 옮기는 프로젝트다. 코드는 코딩 에이전트가 썼고, 개발자 한 명이 방향과 검증 기준을 정했다.

목표는 두 가지다.

- **호환성**: 같은 입력에 대해 출력, 오류 문구, 종료 코드, 생성 파일이 Java 구현과 byte 단위로 같다.
- **성능**: 실행 시간과 메모리 사용량이 기준 구현 이하다.

범위는 언어, 표준 라이브러리 모듈 23개, 렌더러 9종, CLI 전체 명령, REPL, server, formatter, `pkldoc`이다. 여기에 Rust API와 `@pkl-rs/napi`, `@pkl-rs/wasm` 패키지가 더해진다.

## 첫 구현: 빨리 도달하고 끝내지 못했다

첫 구현은 Pkl 0.31.0을 대상으로 기능을 거의 다 만들었지만, 성능 목표와 최종 검증을 통과하지 못했다.

**시작은 빨랐다.** 지침은 "호환성 우선, 성능 최적화는 후순위"였다. 대조할 정답은 Pkl 저장소가 제공하는 기본 테스트뿐이었고, 12일 만에 그 언어 테스트 666개를 모두 맞췄다.

**속도를 따라잡으려고 엔진을 하나 더 얹었다.** 첫 평가기는 Apple의 네이티브 바이너리보다 약 1.9배 느렸다. 닷새 뒤 bytecode VM을 만들기 시작해 6월에 기본 엔진으로 바꿨다. 처음의 평가기도 대조용으로 남겼기 때문에, 두 엔진의 출력이 Apple과도 서로와도 같아야 했다.

**배포 대상은 나중에 붙였다.** WASM과 N-API 바인딩은 7개월째인 8월에 생겼다. 브라우저 폼을 만드는 실제 소비자 프로젝트가 이 WASM을 썼다.

**오라클은 검증하면서 쌓였다.** 기본 테스트가 다루지 않는 영역은 정답을 하나씩 만들어 대조해야 했다. CLI 전체 출력 비교는 6월 237건에서 10월 1,340건으로 늘었다. 패키지 비교, 소비자 프로젝트의 테스트, 진단 메시지 대조, Apple 대비 성능과 메모리 측정이 차례로 더해졌다.

**끝내지는 못했다.** 10월 6일 성능 최적화를 중단했다. 그때 최초 실행 WASM은 소비자 13사례 모두에서 한도인 Apple의 2배를 넘었다. 남은 불일치를 고치는 작업이 7주 더 이어졌지만, 11월 중순에도 테스트 약 1만 개 가운데 21개가 실패했고 최종 검증은 통과하지 못했다.

## 슬롭이 쌓인 과정

슬롭은 그럴듯하지만 목표 달성을 입증하지 못하는 코드와 테스트와 기록을 말한다. 첫 구현에서는 슬롭이 한 번의 결정이 아니라 다섯 단계에 걸쳐 쌓였다. 대조할 정답이 적은 채로 출발한 것이 그 바탕이었다.

### 1. 성능과 배포 대상을 뒤로 미뤘다

구조가 굳은 뒤에 두 번째 엔진, WASM, N-API를 차례로 얹었다. 새 VM은 첫 평가기의 참조 카운트 값 모델을 그대로 빌려 썼다. 9월 실측에서 브라우저 폼을 한 번 편집하는 데 Apple Pkl의 35~145배가 걸렸다.

### 2. "통과"가 증명하는 것이 적었다

기본 테스트만 가지고 출발했기 때문에 대조할 정답이 없는 영역이 넓었다. 숫자는 초록색이었지만 그 숫자가 보장하는 범위는 좁았다.

- CLI 비교 도구는 7월 중순까지 출력을 정규화한 뒤에 비교했다.
- 8월 기준으로 테스트의 76%는 Apple 출력과 대조하지 않는, 손으로 쓴 테스트였다.
- 합성 벤치마크가 Apple의 1.35배까지 내려온 주에, 소비자의 실제 워크로드는 17배 느렸다.
- 다섯 시간이 걸리는 전체 검증을 3주 동안 돌리지 않았다. 다시 돌리자 실패 193건이 한꺼번에 나왔다.

### 3. 활동이 진척처럼 보였다

커밋이 가장 많았던 6월에는 71%가 테스트를 정리하는 커밋이었다. 8월과 9월에는 커밋의 절반이 코드 없이 문서만 고쳤다.

### 4. 기록이 지침을 삼켰다

에이전트가 세션마다 읽는 지침 파일에 진행 상황을 적었다. 10월 초에는 규칙 14KB에 진행 기록 146KB가 붙어 있었다. 따로 둔 작업 로그는 26MB까지 자랐다.

잘라 내도 몇 주 뒤면 다시 자랐다. 세 번째에는 과거 기록을 모두 지우고, 상태를 파일 하나에서 생성하도록 바꿨다.

### 5. 원인을 알고도 같은 구조를 고쳤다

8월 26일의 재설계 계획은 원인을 짚었다. 엔진과 무관한 값 모델, 명시적인 평가 세션, 불변 모듈 그래프, 구조화된 진단이라는 네 경계가 없다는 것이다. 이 계획은 착수되지 않았다.

대신 같은 구조 위에서 수정이 이어졌다. 핵심 VM 파일은 7월 이후 세 배 넘게 불었고, 함수 하나가 7천 줄을 넘는다. 9월에는 모든 테스트를 통과한 변경이 소비자의 정상 입력을 거부했고, 커밋과 되돌림이 하루에 세 쌍 나온 날도 있었다. 성능 목표는 7주 동안 다섯 번 바뀌었다.

엔진 두 개와 거대한 파일 하나, 값 모델이 서로 얽혀 있었다. 네 경계를 넣으려면 사실상 전부 다시 써야 했고, 그래서 다시 썼다.

## 재작성판: 오라클을 물려받고 규칙부터 세웠다

재작성판은 Pkl 0.32.0을 대상으로 한다. 첫 구현이 쌓은 테스트와 실패 기록을 물려받았고, 코드를 쓰기 전에 판정 규칙을 먼저 세웠다.

### 물려받은 것

빈 저장소에서 시작했지만 빈손은 아니었다. 첫 구현이 검증하면서 쌓은 것을 첫날부터 썼다.

- **대조할 대상의 목록.** 첫날 첫 구현의 테스트 소스 758개를 목록으로 만들었다. CLI 출력, 패키지, 진단 메시지, 성능과 메모리까지 대조 범위를 처음부터 잡았다. 첫 구현이 여덟 달에 걸쳐 하나씩 더한 것들이다.
- **회귀 입력.** 첫 구현에서 버그를 드러낸 입력을 가져왔다. 대상 버전이 달라 기대값은 옛 기록을 쓰지 않고 Java 0.32.0에서 다시 뽑았다.
- **실패 기록.** 안티패턴 표는 규칙이 됐고, 구조 진단은 설계의 출발점이 됐다.

### 바꾼 것

| 첫 구현에서 겪은 일 | 재작성판의 규칙 |
| --- | --- |
| 성능을 미뤘다가 엔진이 두 개가 됐다 | 엔진은 하나만 둔다. 시간과 메모리 목표는 처음부터 필수 결과다 |
| WASM을 7개월째에 붙였다 | 첫날부터 native, Node, 브라우저에서 같은 엔진을 돌린다 |
| 정규화 비교와 손으로 쓴 테스트가 통과를 만들었다 | 해시로 고정한 Java 구현과의 byte 비교만 판정으로 인정한다 |
| 미실행과 무시된 테스트가 초록색에 섞였다 | 통과, 실패, 미실행, 미구현을 따로 센다 |
| 지침 파일이 상태 로그가 됐다 | 지침은 규칙 51줄로 두고, 상태와 검증 계약은 다른 문서에 둔다 |

구조도 달라졌다. 첫 구현은 엔진 두 개가 얽혀 있었고, 재작성판은 엔진 하나를 Host 경계로 감쌌다.

| 층 | 첫 구현 | 재작성판 |
| --- | --- | --- |
| 제품 | `pkl-cli`, `pkl-server`. WASM과 N-API는 메모리에 올린 프로그램만 평가 | CLI, `pkldoc`, server, REPL, N-API 애드온, `pkl-wasm` |
| 플랫폼 접점 | `pkl-core`가 두 엔진을 묶는다 (26.9만 줄) | `pkl-host-native`와 JS Host가 Host 인터페이스를 구현한다 |
| 엔진 | `pkl-bytecode` (기본 엔진, 26.0만 줄)가 `pkl-treewalker` (값 모델과 대조용, 18.1만 줄)에 의존한다 | `pkl-runtime` 하나 (32.0만 줄) |

줄 수는 2026-11-23 기준 `crates/` 아래 Rust 파일이다.

엔진은 파일시스템이나 네트워크에 직접 닿지 않고, Host 인터페이스를 통해서만 플랫폼을 쓴다. 그래서 같은 엔진이 CLI, Node.js, 브라우저에서 같은 결과를 낸다.

### 진행

| 단계 | 기간 | 기록된 결과 |
| --- | --- | --- |
| 기준선과 구조 실험 | 10-20 | 정답의 출처를 고정했다. 세 실행 환경에서 6,078건 일치 |
| 언어 의미론 | 10-20 ~ 11-20 | 4,575건 중 4,574건 통과 |
| 표준 라이브러리, Host, 제품, 바인딩 | 11-20 ~ 11-21 | 차등 검증 769건 모두 일치 |
| 성능과 안정성 | 11-22 ~ 11-23 | 워크로드 15개 모두 Apple native-image보다 빠르고 가볍다 |

수치는 모두 로컬 macOS arm64에서 기록한 것이다.

### 재작성판도 두 번 미끄러졌다

**증거를 쌓는 일이 본업이 됐다.** 첫 18일 동안 커밋의 57%에는 코드가 없었고, 정답 관측 파일 49만 개가 저장소에 쌓였다. 11월 5일 에이전트는 언어 의미론 단계에만 8~12주가 더 든다고 추정했다. 이 추정은 같은 날 철회됐고, 중복 검증과 중복 기록을 줄이는 규칙 세 개가 지침에 들어갔다. 그 단계는 보름 뒤에 닫혔다.

**검증을 통과한 것처럼 꾸민 산출물이 나왔다.** 그 직후의 미커밋 작업에서 결과 디렉터리를 조립하는 스크립트, 런타임에 하드코딩한 오류 문자열, 검증 우회 조건이 발견됐다. 보고서는 이를 무결성 위반으로 규정했고, 커밋하기 전에 전부 철회했다.

첫 구현과의 차이는 미끄러지지 않았다는 데 있지 않다. 위반으로 판정할 규칙이 먼저 있었다는 데 있다.

### 남은 것

- 저장소는 스스로 `release_ready: false`라고 적는다. 호스팅 CI와 macOS arm64 외 6개 플랫폼이 검증되지 않았다.
- 11월 20일 이후 단계의 원시 증거는 커밋되지 않았다. 저장소만으로는 다시 감사할 수 없다.
- 마지막 이틀의 최적화로 빠른 경로가 급히 늘었고, 리뷰가 그 안에서 의미론 버그를 여럿 찾았다.

## 잘된 점과 잘못된 점

가장 잘된 일은 첫 구현이 쌓은 오라클과 실패 기록을 재작성판이 물려받은 것이다. 가장 큰 잘못은 완료 기준 없이 오래 달린 것이다.

**잘된 점**

- **첫 구현이 오라클을 쌓았다.** 기본 테스트에서 출발해 CLI, 패키지, 소비자, 진단까지 대조 범위를 넓혔다. 재작성판은 이것을 출발점으로 삼았다.
- **실제 소비자에 출하했다.** 첫 구현의 WASM을 쓴 프로젝트가, 내부 테스트가 놓친 버그를 열 건 넘게 찾았다.
- **실패를 사례와 함께 적었다.** 첫 구현의 "안티패턴 (전부 실제 발생)" 표가 재작성판 규칙의 밑바탕이 됐다.
- **정답을 제품 밖에 두었다.** 재작성판에서는 에이전트가 자기 출력으로 기대값을 만들 수 없다.
- **엔진 하나와 Host 경계.** 재작성판은 WASM과 N-API 패키지를 만들 때 엔진을 고치지 않았다.
- **스스로 철회했다.** 근거 없는 일정 추정과 꾸민 산출물을 문서에 남기고 되돌렸다.

**잘못된 점**

- **완료 기준이 늦었다.** 첫 구현은 인증 기준을 문서로 정하기까지 다섯 달 반이 걸렸다.
- **성능과 배포 대상을 나중에 다뤘다.** 그때는 값 모델과 실행 방식을 바꿀 수 없었다.
- **활동량을 진척으로 읽었다.** 커밋 수와 통과 건수가 늘어나는 동안, 남은 실패는 세지 않았다.
- **진단하고도 계속 고쳤다.** 구조 문제를 짚은 뒤에도 석 달을 같은 구조 위에서 보냈다.
- **재작성판에서도 증거가 불어났다.** 관측 파일 때문에 저장소가 9.9GB가 됐고, 계획 문서는 654KB다.
- **재작성판은 한 플랫폼에서만 검증됐다.** 마지막 커밋 29개는 문서에 반영되지 않았다.

## 다음 프로젝트에 가져갈 것

에이전트는 코드를 빨리 쓰지만 "끝났는가"를 스스로 판정하지 못한다. 그 판정을 사람이 미리 설계해야 한다.

1. **판정 기준을 코드보다 먼저 만든다.** 정답의 출처를 고정하고, 통과와 실패와 미실행을 따로 센다.
2. **오라클을 먼저, 두껍게 쌓는다.** 기본 테스트만으로는 얇다. CLI 출력, 실제 워크로드, 진단 메시지까지 대조 범위를 넓힌다. 다시 쓸 때 가져갈 수 있는 것은 코드가 아니라 오라클이다.
3. **에이전트가 정답을 만들 수 없게 한다.** 기대값과 통과 조건을 건드리는 변경은 사람이나 독립된 검토가 본다.
4. **성능과 배포 대상을 첫 주에 실측한다.** WASM이 목표라면 첫 주에 브라우저에서 돌린다.
5. **엔진은 하나만 둔다.** 대조용 구현이 필요하면 제품 밖의 것을 쓴다.
6. **성능은 실제 워크로드로 잰다.** 합성 벤치마크의 평균은 이상치를 가린다.
7. **지침 파일에는 규칙만 둔다.** 상태는 한 곳에서 생성하고 이력은 git에 맡긴다. 지침 파일이 자라면 경고로 본다.
8. **활동량이 아니라 남은 실패를 본다.** 전수 목록이 줄어드는지 확인하고, 느린 전체 검증을 정기적으로 돌린다.
9. **빠른 경로는 느린 경로와 비교해 검증한다.** 같은 입력을 두 경로로 돌리는 테스트를 최적화와 함께 넣는다.
10. **다시 쓰는 기준을 미리 정한다.** 구조 문제를 진단했으면, 같은 구조를 고치는 데 쓸 예산을 정한다. 오라클이 쌓여 있으면 다시 쓰는 비용은 생각보다 작다. 이번에는 5주였다.

## 의의

같은 목표를 두 번 시도한 덕분에, 에이전트 개발의 속도와 품질이 어디에서 나오는지를 비교로 확인할 수 있었다.

- **대규모 호환 포팅은 에이전트로 가능하다.** 언어 런타임과 도구 일체를 5주 만에 만들었다. 정답을 내놓는 기준 구현이 있는 문제였기에 가능했다.
- **오라클이 속도를 정했다.** 두 시도 모두 여러 에이전트와 모델을 썼고, 두 시도 모두 미끄러졌다. 달랐던 것은 대조할 정답의 양과 미끄러짐을 되돌리는 규칙이었다.
- **재작성판의 5주는 첫 구현의 9개월 위에 서 있다.** 첫 구현이 검증하면서 쌓은 오라클, 실패 기록, 구조 진단이 재작성판의 출발점이었다.

이 노트의 수치는 두 저장소의 git 이력과 문서에서 뽑았다. 빌드나 테스트를 다시 실행해 확인한 것은 아니다.
