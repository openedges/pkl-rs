# Pkl 0.32.0 Source Inventory

[compatibility/inventory.json](../compatibility/inventory.json) is the deterministic,
machine-readable source inventory generated by [tools/inventory.py](../tools/inventory.py).
It enumerates the pinned upstream surface for implementation and test mapping. It is
not a compatibility result, a compiler-produced ABI listing, or a count of passing tests.
Every item currently records `implementation.state = unimplemented` with no links and
`tests.state = unmapped` with no case IDs. Upstream declaration/builtin matches are
separate from those implementation and test states.

Run from the repository root with Python 3.9 or later and Git:

```sh
python3 tools/inventory.py
python3 tools/inventory.py --check
python3 -m unittest discover -s tools/tests -p test_inventory.py -v
```

The first command writes the inventory; `--check` regenerates in memory and compares
the entire JSON file as bytes. Missing inventory files, omitted items, changed states,
changed source contents, added or removed selected sources, and a checkout revision
different from `references.lock` fail the check. It reads tracked sources plus untracked,
non-ignored sources so a newly added source cannot silently evade the census. Source
hashes also detect changes that preserve declaration names, such as a changed default
value. This tool reads the reference checkout and does not modify it. Reference pin and
working-tree validation remain the responsibility of `cargo xtask verify`.

## Provenance and Identity

`baseline` records the upstream URL, version, revision, checkout path, and a source URL
template. Each item's `source.path` is relative to that checkout and `source.line` is
one-based. Substitute those fields into `baseline.source_url_template` to obtain a
revision-pinned source link. File resources use line 1 as a file-level location.
`sources` records raw SHA-256 hashes, module names, and extracted item counts for every
selected file, including files with no extracted declarations. `counts` exposes totals
by category, module, API scope, and stdlib visibility.

Identities combine category, source path, symbol, and a source signature hash where
needed. Overloads remain distinct. Repeated identical headings/calls receive a line
suffix. These are source identities rather than stable binary ABI identifiers; source
signature or repeated-heading location changes can change an ID. Do not edit the
generated JSON to mark implementation or tests complete: add durable mapping input and
validate its links before extending the generator to accept completion evidence.

## Extraction Contract

The census includes all files under tracked production `src/main/` and annotation
processor `src/generator/` trees, all `stdlib/*.pkl` modules, and AsciiDoc sources in
the language reference, binding specification, CLI, Java/Kotlin binding, and documentation
tool reference sections. Test-support and build-logic production trees remain visible in
the module totals. Test inputs belong to the separate discovery manifest.

| Category | Extracted evidence |
| --- | --- |
| `stdlib` | Module identity; declared classes, aliases, functions, and properties at module/class scope; `external`, `hidden`, and local/public visibility |
| `builtin` | Specialized handwritten external node classes, inherited external-node base kinds, module/class/member `PklName` overrides, and inferred registry identities |
| `language_token` | Every enum token in `Token.java`, including reserved tokens, punctuation, and string continuation tokens |
| `language_parser` | Parse, lex, next, and skip routines in both parser implementations and the lexer |
| `specification` | Reference headings, including language behavior, binary encoding, and message passing |
| `renderer` | Output format enum entries plus concrete stdlib renderer classes, including the bytes renderer in `pkl:pklbinary` |
| `cli_command`, `cli_argument`, `cli_option` | Explicit command names, positional argument names, option aliases and negative flags in command/tool entry points; option source configuration includes following defaults and validators |
| `protocol_tag`, `protocol_field` | Message codes and literal key candidates in MessagePack encoders/decoders; linked source retains message order and optionality |
| `java_api` | Source-visible public/protected types, constructors, methods, fields, implicit interface members, enum constants, and record component accessors; type nesting and overload signatures |
| `kotlin_api` | Public source candidate types, functions, properties, aliases, receiver functions, and primary constructor properties; private/internal/protected declarations are excluded |
| `resource` | Production resources, including pkldoc fonts, images, styles, and scripts, with raw source hashes |

Source-visible JVM declarations span evaluator/configuration APIs, external readers,
server/message types, Java/Kotlin generators, pkldoc, the formatter, executor, and
Gradle integration. Public implementation classes are retained but marked
`api_scope = internal-source-candidate` for AST, runtime, stdlib, utility, and annotation
processor paths. Other declarations remain `source-candidate`: Java visibility alone
does not imply a supported public integration contract.

At the pinned revision the inventory contains 985 source/resource files, 24 stdlib
modules, and 542 external member declarations. All 542 reconcile with specialized
source-derived builtin registration identities in both directions. Matching uses
the member kind as well as its qualified name: `IntSeq.step` is both a property and
a method. Local externals such as `EvaluatorSettings.resolvePath` remain required
builtins. Shared unspecialized node helpers are excluded. Registry naming follows
the pinned `MemberRegistryGenerator.java`; this is a source cross-check, not evidence
that generated registries were built or that any Rust builtin works.

## Limits and Remaining Mapping Work

The scanner recognizes comments, strings, nesting, visibility, declaration indentation,
and source headers; it is not a full Java, Kotlin, Pkl, or AsciiDoc parser. The pinned
stdlib uses top-level classes and two-space class members, which the Pkl scanner relies
on. It lists declared members and does not expand inherited members or resolve types.
Annotations, complex string interpolation, unusual formatting, multiple declarations on
one line, and new syntax can require scanner updates and review. The regression suite
tests representative extraction boundaries, not every upstream syntax form.

The JVM inventory does not expand inherited APIs, synthetic bridges, Kotlin generated
getters/component/copy/default-argument methods, or all annotation-processor output.
It does not perform overload resolution or infer an exact Java/Kotlin binary ABI.
Compiled API export and existing-client linkage tests remain necessary before declaring
JVM adapter compatibility. Helpers classified by source path may require reclassification.

CLI aliases/defaults supplied by Clikt, inherited option applicability per command,
dynamically generated shell-completion arguments, evaluated default expressions, help
text, exit codes, and REPL transcripts need oracle execution. Option configuration is
source evidence rather than an evaluated default-value table. Codec key candidates
are not a per-message schema and do not establish required fields, ordering, request
lifecycle, or wire equivalence. Parser routine and specification heading counts are
not an exhaustive set of semantic edge cases; reserved tokens are not implemented
language features. Runtime diagnostics and behavioral requirements need individual
test mappings beyond their linked implementation/specification files.

Source census hashes ensure reviewable source changes even when a declaration extractor
does not understand a file. They do not prove that every semantic requirement has been
extracted. Full compatibility requires reviewed feature/API mappings, Java-generated
expectations, raw-byte differential execution, and target/client checks under
[TESTING.md](../TESTING.md). Empty implementation/test links remain unimplemented and
unmapped requirements; they are never counted as passes.
